# خطة تظهير الشيكات في Yalla Accounts  
*Accounting + Logic + UI + DB*

> الهدف: تنفيذ عملية **تظهير الشيكات** من أول استلام الشيك من العميل  
> وحتى تحويله إلى شيك صادر للمورّد، مع ضبط **القيود المحاسبية، الذمم، GL،  
> وقواعد البيانات والواجهات** بدون أي لخبطة.

---

---

## 1) المرحلة المحاسبية (Business Rules)

### 1.1 تعريف القيود قبل وبعد التظهير

#### أ) عند استلام الشيك من العميل (قبض):
- مدين: **أوراق القبض (Incoming Cheques / Cash in Transit)**  
- دائن: **حساب العميل / شركة التأمين**

#### ب) عند التظهير (Endorsement) – نريد اعتماد نموذج موحّد:

1. **إخراج الشيك من أوراق القبض**  
   - مدين: حساب الجهة الجديدة (المورّد / الطرف المستفيد)  
   - دائن: أوراق القبض (Incoming Cheques)

2. **تسجيل شيك صادر (أوراق دفع)**  
   - مدين: أوراق الدفع (Outgoing Cheques / Cheques Payable)  
   - دائن: حساب المورّد / الطرف المستفيد

> محصلة العملية:
> - لا تعديل على ذمة العميل (يظل مسدد بنفس الشيك).  
> - ذمة المورّد تزيد بقيمة الشيك.  
> - أوراق القبض تقل.  
> - أوراق الدفع تزيد.

## 2) المرحلة الخاصة بقاعدة البيانات (Database Rules)

### 2.1 جدول `cheques`

تأكد أن الجدول يحتوي على الحقول التالية (أو ما يعادلها في مشروعك):

- `id` : TEXT (UUID)
- `chequeNumber` : TEXT
- `type` : TEXT  // "IN" أو "OUT"
- `status` : TEXT  // RECEIVED, ENDORSED, CLEARED, RETURNED, ...
- `fromPartyId` : TEXT  // العميل الأصلي
- `toPartyId` : TEXT  // الجهة التي سيتم التظهير لها (مورّد/طرف آخر)
- `amount` : REAL
- `issueDate` : TEXT
- `dueDate` : TEXT
- `endorsementDate` : TEXT (nullable)
- `relatedPaymentId` : TEXT (nullable)  // السند/الدفع الناتج عن التظهير

### 2.2 جدول `payments`

سطر الدفع الناتج عن التظهير يجب أن يكون:

- `id` : TEXT
- `type` : TEXT  // "CHEQUE_OUT" أو ما يقابله
- `isIncome` : INTEGER  // 0 لأنه دفع خارج من الورشة
- `amount` : REAL  // نفس مبلغ الشيك
- `supplierId` : TEXT  // الجهة الجديدة المستفيدة
- `chequeId` : TEXT  // ربط الدفع بالشيك
- `gl_entry_id` : TEXT  // ربطه بقيد GL
- `paymentDate` : TEXT  // تاريخ التظهير

### 2.3 جداول GL (`gl_entries` + `gl_lines`)

يُنشأ GL Entry جديد عند التظهير:

- `gl_entries`:
  - `id`, `date`, `description`, `source_type = "CHEQUE_ENDORSEMENT"`, `source_id = chequeId`

- `gl_lines`:  
  1. سطر لعكس أوراق القبض (Debit supplier / Credit incoming_cheques)  
  2. سطر لإثبات أوراق الدفع (Debit outgoing_cheques / Credit supplier)

### 2.4 جدول `suppliers` / `accounts`

- تحديث رصيد المورّد من خلال GL فقط (أفضل) أو عن طريق حقل `balance` في جدول `suppliers` إذا كان لديك حقل مباشر.  
- التأكد من أن حساب المورّد مستخدم في GL Lines الصحيحة.

## 3) المرحلة الخاصة بالواجهات (UI / UX Rules)

### 3.1 شاشة الشيكات الواردة (Incoming)

- زر/إجراء جديد لكل شيك: **[تظهير]**.  
- عند الضغط:
  - فتح Dialog لاختيار:
    - المورّد (أو الطرف) الذي سيتم التظهير له.
    - تاريخ التظهير (افتراضي = اليوم).
  - عند تأكيد العملية → استدعاء Service التظهير.

- بعد نجاح التظهير:
  - الشيك يختفي من قائمة الوارد.  
  - Snackbar / Toast: "تم تظهير الشيك بنجاح".

### 3.2 شاشة الشيكات الصادرة (Outgoing)

- الشيكات المظهّرة تظهر فيها تلقائيًا:
  - النوع: "صادر"  
  - الحالة: "مظهّر" أو "قيد التحصيل"  
  - اسم المورّد/الطرف في عمود المستفيد.

### 3.3 شاشات أخرى يجب أن تتأثر

- شاشة **الموردين**:
  - رصيد المورّد يرتفع بقيمة الشيك المظهّر.
  - في كشف حساب المورّد يظهر قيد جديد (Cheque Endorsement).

- شاشة **الدفعات (سندات الصرف)**:
  - سند صرف جديد مربوط بالشيك.

- شاشة **دفتر الأستاذ / GL Reports**:
  - Entry جديد عنوانه "تظهير شيك رقم XXX".

## 4) المرحلة البرمجية (خطة التنفيذ في الكود)

### 4.1 إنشاء Service موحّد للتظهير

إنشاء ملف جديد مثلاً:

- `lib/features/cheques/services/cheque_endorsement_service.dart`

ويحتوي دالة أساسية:

- `ChequeEndorsementService.endorseCheque({ required String chequeId, required String supplierId, required DateTime endorsementDate })`

### 4.2 داخل `endorseCheque` – منطق موحّد (Pseudocode)

1. جلب بيانات الشيك من DB.  
2. التحقق:
   - أن نوعه IN.  
   - أن حالته تسمح بالتظهير (مثلاً RECEIVED، ليس مظهرًا من قبل).  
3. فتح Transaction عبر `DBService.inTx`:
   - تعديل سجل الشيك:
     - `type = OUT`
     - `status = "ENDORSED"`
     - `toPartyId = supplierId`
     - `endorsementDate = endorsementDate`
   - إنشاء سجل Payment جديد:
     - `type = CHEQUE_OUT`
     - `isIncome = 0`
     - `amount = cheque.amount`
     - `supplierId = supplierId`
     - `chequeId = chequeId`
   - إنشاء GL Entry + GL Lines:
     - قيد عكس أوراق القبض.  
     - قيد إثبات أوراق الدفع.  
   - ربط `payment.gl_entry_id` بـ GL Entry.  
4. إنهاء Transaction بنجاح.  
5. إطلاق Event (اختياري) لتحديث Providers:
   - `chequeProvider.refresh()`
   - `suppliersProvider.refresh()`
   - `paymentsProvider.refresh()`
   - `glProvider.refresh()`

## 5) المرحلة الخاصة بالبروفايدرز (Riverpod / State)

### 5.1 `cheque_provider.dart`

- إضافة method:  
  - `Future<void> endorseCheque(chequeId, supplierId, date)`  
  - تستدعي `ChequeEndorsementService.endorseCheque`  
  - ثم تقوم بعمل `ref.refresh` للقوائم.

### 5.2 `suppliers_provider.dart`

- لا يحتاج منطق خاص إذا كانت الذمم تُحسب من GL.  
- إذا كان هناك حقل `balance` مباشر للمورّد:
  - يتم تحديثه داخل الـ Service أو بواسطة Event.

## 6) المرحلة الخاصة بالاختبارات (Testing Plan)

### 6.1 سيناريو اختبار A – شيك واحد

1. إنشاء عميل جديد.  
2. إصدار فاتورة له بقيمة 1000 ILS واستلام شيك بنفس القيمة.  
3. التحقق:
   - يظهر الشيك في قائمة IN.  
   - GL: أوراق القبض مدين، العميل دائن.  
4. تظهير الشيك لمورّد "X".  
5. التحقق:
   - الشيك اختفى من IN، ظهر في OUT.  
   - Payment جديد نوعه CHEQUE_OUT.  
   - GL:
     - عكس أوراق القبض.  
     - إثبات أوراق الدفع للمورّد.  
   - ذمة العميل: كما هي لا تتغير.  
   - ذمة المورد: زادت 1000.

### 6.2 سيناريو اختبار B – تقارير

- فتح كشف حساب المورد → يظهر فيه قيد التظهير.  
- فتح تقرير GL → Entry واحد فيه 2–4 أسطر توضح العملية.  
- فتح تقرير ذمم الموردين → رصيده يشمل المبلغ.

### 6.3 سيناريو اختبار C – حالات خطأ

- محاولة تظهير شيك تم تظهيره سابقًا → رسالة خطأ "لا يمكن تظهير الشيك مرة أخرى".  
- محاولة تظهير شيك حالته RETURNED → ممنوع.  
- محاولة تظهير شيك OUT أصلاً → ممنوع.

## 7) المرحلة العملية (العمل ملف مقابل ملف)

سنمشي بالتنفيذ معًا وفق الترتيب التالي:

1. **توثيق الجداول** (تحديث `cheques` و `payments` لو ناقص أي حقل).  
2. إنشاء ملف: `cheque_endorsement_service.dart`.  
3. تعديل `cheque_model.dart` إذا احتجنا حقول جديدة (type, status, toPartyId, endorsementDate…).  
4. تعديل `cheque_provider.dart` لإضافة `endorseCheque`.  
5. تعديل شاشة الشيكات الواردة لإضافة زر "تظهير" وربطه بالـ provider.  
6. تعديل شاشة الشيكات الصادرة لعرض الشيكات المظهّرة.  
7. التأكد من ظهور الحركة في:
   - كشف حساب المورد.  
   - سجلات GL.  
   - قائمة الدفعات (إذا موجودة).  
8. تشغيل الاختبارات الثلاثة A/B/C على داتا تجريبية.

> تنفيذ الكود سيتم دائمًا بأسلوب:
> - ترسل لي الملف الحالي.  
> - أرجع لك نسخة كاملة جديدة جاهزة للاستبدال.  
> - نختبر ثم ننتقل للملف التالي.
