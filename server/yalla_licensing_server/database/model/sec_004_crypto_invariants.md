# SEC.004 cryptographic authority invariants

1. The Yalla Licensing Server is the only authority allowed to issue signed licenses.
2. The initial license signing algorithm is Ed25519. The envelope identifies it as EdDSA.
3. License payload bytes are RFC 8785 JSON Canonicalization Scheme (JCS) UTF-8 bytes.
4. signed_payload_hash is lowercase SHA-256 hex of the exact canonical payload bytes.
5. Signatures and raw public keys use base64url without padding.
6. Production private signing-key bytes are never stored in PostgreSQL, the Git repository, ZIP patches, the desktop client, or client SQLite.
7. PostgreSQL stores only the public key and an opaque server-side provider reference (KMS/HSM/secret store).
8. At most one signing key may be ACTIVE for issuance at a time.
9. Key lifecycle is one-way: STAGED -> ACTIVE -> RETIRED, with REVOKED reachable from any non-revoked state.
10. Once a key leaves STAGED, its identity, algorithm, public key, and provider reference are immutable.
11. An ACTIVE license must contain signing_key_id, payload schema version, payload, payload hash, algorithm, signature, and signed_at.
12. A license may only be activated if it was signed inside the referenced key validity window.
13. RETIRED keys are retained for historical verification but cannot be selected for new issuance.
14. REVOKED keys are not trusted once revocation state is known; online validation will distribute/refresh that state in a later stage.
15. The signed payload is bound to organization_id, subscription_id, license_id, device_id, installation_id, device public-key hash, validity, and entitlement revision.
16. No production key is generated by this desktop-side patch. Production provisioning happens only inside the actual server secret boundary.
17. Client database version remains v63; SEC.004 adds no licensing tables to client SQLite.
